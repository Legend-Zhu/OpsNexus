# 告警规则删除级联停止监控方案

> 版本：v1.0
> 日期：2026-08-25
> 状态：已实施（后端 + 前端完成；`go test ./internal/alertrule/` 7 例全过，`vue-tsc` 通过）
> 关联：docs/集群纳管清单方案.md、docs/Worker-设计方案.md、docs/OpsGaurdWeb-设计方案.md

## 一、背景与问题

### 1.1 现象

集群详情页「告警规则」Tab 删除规则时提示：

> 删除规则 es-yj4？（不会改动服务当前已生效的监控配置）

提示本身是如实的，但它暴露了一个设计缺陷：**删除规则之后，监控照常运行、告警照常产生，而唯一能停止监控的入口（规则行上的「下发」按钮）随着规则一起被删掉了**。用户想停监控，只能重新手工建一条 `enabled: false` 的同名规则再下发——本末倒置。

### 1.2 现状代码链路

告警规则与生效监控是"配置源 → 生效副本"两层结构，删除只作用于源：

| 层 | 实体 | 位置 |
|---|---|---|
| 配置源（规则库） | `store.AlertRule`，LevelDB 键 `alertrule/<cluster>/<service>` | `server/internal/store/notify.go:209` |
| 生效副本 A（swarm 服务） | Worker 进程内存中 `monitor.Manager` 注册的监控 job，由最后一次 `Update` 下发的 `config.Monitoring` 驱动 | `Worker/internal/monitor/manager.go` |
| 生效副本 B（纳管对象） | 集群记录纳管清单条目的 `Inventory.Items[i].Monitoring` 字段，由 server 端 `invmonitor` 探测循环每轮读取执行 | `server/internal/invmonitor/service.go:129` |

删除接口只做一件事——删 LevelDB 键：

- 前端 `removeRule`：`web/src/views/clusters/Detail.vue:764-769`，调 `alertRuleApi.remove`（`web/src/api/index.ts:172`）后仅刷新列表；
- 路由：`server/internal/router/router.go:194` `DELETE /v1/alertrules/:cluster/:service`；
- Handler：`server/internal/api/system.go:251-267`；
- Service：`server/internal/alertrule/service.go:68-78` `Delete` —— 校验存在后仅 `st.DeleteAlertRule`，**无任何 Worker 调用、无清单更新**。

而下发（`Apply`，`service.go:87-142`）是有逆操作的语义需求的：它把规则推到生效点。**`Apply` 有正向推送，`Delete` 却没有逆向停止**——操作的不对称是问题本质。

### 1.3 附带的复活问题

纳管清单保存时会反向同步规则（`SyncFromInventory`，`service.go:171-211`，调用点在 `api/inventory.go:148`）：清单中带启用监控的条目会 upsert 对应规则。因此**纳管来源的规则即使被手动删除，只要清单条目监控仍启用，下次保存清单规则就会复活**——而生效探测读的是清单本身，删规则对停止探测毫无作用。

---

## 二、修复原则

1. **删除 = Apply 的逆操作**：删除规则时，先把该规则在生效点的监控停掉，再删规则记录。
2. **停止是幂等的**：规则可能从未下发过，停止动作必须可以安全重复执行（对已无监控的目标执行停止不报错）。
3. **fail-fast**：停止失败（Worker 不可达、Update 失败）时**保留规则**并报错——规则还在，状态就仍可补救；绝不制造"规则没了、监控还在跑"的悬空状态。
4. **留逃生门**：提供 `force` 参数，允许用户在明知生效配置无法停止（如 Worker 长期下线）时强删规则，但必须显式确认，且响应中如实报告"监控未停止"。
5. **目标判定与 Apply 完全一致**：同名歧义时（swarm 服务与纳管清单同名）沿用 Apply 的 swarm 优先语义，只停 Apply 会下发到的那一个目标，不扩大化清理。

## 三、设计方案

### 3.1 后端 Service：`alertrule/service.go`

签名变更：

```go
// 旧
func (s *Service) Delete(clusterName, service string) error

// 新
func (s *Service) Delete(ctx context.Context, clusterName, service string, force bool) (*DeleteResult, error)

// DeleteResult 删除结果。
type DeleteResult struct {
    Deleted string `json:"deleted"`            // "cluster/service"
    Stopped bool   `json:"stopped"`            // 生效配置是否已成功停止
    StopErr string `json:"stopError,omitempty"` // force 删除时停止失败的原因
}

// ErrStopFailed 停止生效监控失败（规则未删除；可重试或 force 强删）。
// Handler 据此精确映射 502（区别于 500 存储错误）。
type ErrStopFailed struct{ Err error }
```

执行流程：

1. `st.GetAlertRule` 校验存在，不存在返回 `ErrNotFound`（行为不变）。
2. **停止生效配置**（以下两步互斥，目标判定与 `Apply` 相同；实现上比 Apply 更严格一处：`GetWorkload` 返回传输错误（Worker 不可达/超时）时视为**停止失败**而非静默回退清单——删除不能像下发那样容忍"不确定"，仅当 Worker 明确返回 `codes.NotFound`（服务确不存在）才回退清单，见 `isServiceNotFound`）：
   - `cli.GetWorkload(ctx, service)` 成功（是 swarm 服务）：复用 Apply 的 config 拼装——将 `service.go:109-131` 内联的拼装逻辑抽成共享函数 `buildWorkloadConfig(d, monitoring) (yamlText string, err error)`，Apply 传 `r.Monitoring`，Delete 传 `store.Monitoring{Enabled: false}`；然后 `cli.Update` 下发。Worker 侧已验证：`Manager.Register` 先取消该服务的旧任务，`mc == nil || !mc.Enabled` 时不再注册新任务（`Worker/internal/monitor/manager.go:52-60`），监控必停。`op.Status == "failed"` 视为停止失败。
   - `GetWorkload` 失败（非 swarm 服务）：在集群纳管清单找同名条目（逻辑同 `applyToInventory`，`service.go:146-165`），若 `item.Monitoring != nil` 则置 `nil`，经 `clusters.UpdateInventory` 落库。`invmonitor` 下一轮探测即跳过该条目（`invmonitor/service.go:129` 判断 `item.Monitoring != nil && item.Monitoring.Enabled`）。
     注意：此处直接调 `clusters.UpdateInventory`，**不会触发 `SyncFromInventory`**（该调用点在 `api/inventory.go:148` 的保存清单 handler 中），与现有 `applyToInventory` 一致，无规则复活问题。条目不存在或监控本就为空时视为"已停止"（幂等）。
3. 停止成功（或无生效配置可停）后 `st.DeleteAlertRule` 删除记录。
4. 停止失败时：`force == false` 返回错误、**不删记录**；`force == true` 照删，结果中 `Stopped: false` 并填 `StopErr`。
5. 集群本身不存在（`WorkerClient` 返回集群未找到）时视为无生效点，直接删记录（`Stopped: true`）；其他 `WorkerClient` 错误（瞬时）按停止失败处理。

### 3.2 后端 Handler：`api/system.go:251-267`

- 透传 `c.Request.Context()`（停止操作需要超时控制）；
- 新增读取 `c.Query("force") == "true"`；
- 成功：200 + `DeleteResult`；
- `ErrNotFound`：404（不变）；
- 非 force 停止失败：**502**（与 `ApplyAlertRule` 失败码，`system.go:245`，保持一致），错误文案明确规则已保留，如 `停止监控失败，规则未删除：<原因>`。

### 3.3 前端

**`web/src/api/index.ts:172`**：

```ts
// 旧
remove: (cluster: string, service: string) => del<{ deleted: string }>(`/v1/alertrules/${cluster}/${service}`)
// 新
remove: (cluster: string, service: string, force = false) =>
  del<{ deleted: string; stopped: boolean; stopError?: string }>(
    `/v1/alertrules/${cluster}/${service}${force ? '?force=true' : ''}`)
```

**`web/src/views/clusters/Detail.vue:764-769` `removeRule`**：

1. 确认文案改为如实描述新行为：
   `删除规则 ${row.service}？将同时停止其已生效的监控（swarm 服务向 Worker 下发禁用配置；纳管对象清除清单中的监控声明）`
2. 按响应分支提示：
   - `stopped === true`：`已删除并停止监控`；
   - `stopped === false`（force 场景）：警告 `规则已删除，但监控未能停止：${stopError}`；
3. 非 force 请求失败（502）时二次确认：
   `停止监控失败（规则已保留）：${msg}。是否强制删除？强制删除后监控将继续运行，且无法再通过规则停止。`
   确认后以 `force: true` 重发。

### 3.4 契约兼容性

- 只增不改：`DELETE /v1/alertrules/:cluster/:service` 路径不变，不带 `force` 参数时行为语义仅从"静默留尾巴"变为"级联停止"；响应体为原 `{deleted}` 的超集。
- 不动数据模型（`store.AlertRule`、`InventoryItem` 无变更），不动 `SyncFromInventory` 语义。

## 四、行为对照

| 场景 | 现状 | 修复后 |
|---|---|---|
| 删除已下发的 swarm 规则 | 监控继续跑，无补救入口 | 向 Worker 下发 `enabled: false` 停止监控，再删规则 |
| 删除已下发的纳管规则 | 探测继续，下次保存清单规则复活 | 清单条目 `Monitoring` 清空，探测停止，不复活 |
| 删除从未下发的规则 | 仅删记录 | 幂等停止（无副作用）+ 删记录 |
| 停止失败（Worker 不可达） | —（删除从不失败） | 默认：报错、规则保留；`force`：强删、如实报告未停止 |
| 集群已删除 | 孤儿规则可删 | 无生效点，直接删记录 |

## 六、顺带发现的隐患（建议另立任务，不在本方案范围）

### 6.1 Worker 重启静默丢失全部监控任务

swarm 服务的监控 job 只存在于 Worker 进程内存（`monitor.Manager` 的 `cancels/active` map），Worker 既不持久化监控配置，也没有启动时按现存服务重建监控的逻辑。**Worker 一重启，所有监控静默消失**——管理端规则库与纳管视图仍显示"已配置监控"，实际已无人探测，形成假安全感。与本次修复的"已生效"语义直接矛盾：生效副本的生命周期比配置源短，且消失时无任何通知。
建议方向：Worker 启动时按纳管的 swarm 服务及其最后一次 config 重建监控；或管理端感知 Worker 重启事件后自动重新下发。

### 6.2 删除集群不清理孤儿规则

`OnClusterRemove` 回调目前只注册了 ingest（`cmd/server/main.go:151`）与 idpTunnel（`cmd/server/main.go:239`）两个清理器，`alertrule/*` 键不在其中。删除集群后，该集群的告警规则全部变成孤儿记录残留在规则库，污染规则列表（若列表不按集群过滤）且永不可下发。
建议方向：在 `alertrule.Service` 上提供 `RemoveCluster(clusterName)` 并按 `alertrule/<cluster>/` 前缀扫描删除，注册进 `OnClusterRemove`。

**已修复（2026-08-25）**：`alertrule.Service` 新增 `RemoveCluster`（`ListAlertRules(cluster)` 后逐条删除），注册进 `OnClusterRemove`（`cmd/server/main.go`，失败记日志不阻塞集群删除）。集群记录先落库删除、回调后触发，清理时机正确。测试：`TestRemoveClusterPurgesRules`（只清目标集群，其他集群规则保留）。
