## 一、背景与原则

### 1.1 现状的问题

集群详情页的"容器与服务"/"中间件"标签页只展示 **swarm service**（`docker service ls`）。用户用 `docker run` 部署的中间件（r-nacos、grafana、nginxwebui）和 231 上裸跑的 AI 服务等**看不到**，因为它们不是 swarm service。

之前曾尝试"自动扫描节点上的 standalone 容器并归类为中间件"——**这个方向是错的**。自动探测不可控、不可审计、分类靠猜，不符合运维管理的要求。

### 1.2 核心原则

**不探测、全靠配置、明确类型。** 一个集群要管哪些对象，全部通过配置声明：

1. **OpsGaurd 部署的 swarm service**：部署配置（`config.Service` YAML）就是声明——name/image/labels.category/monitoring 在部署时已明确，不需要额外配置。`docker service ls` 列出它们是"列举自己的编排对象"，不是探测。
2. **外部对象**（standalone container、host service）：必须在**纳管清单（Inventory）**里显式声明，否则不显示、不监控。不自动扫描、不猜测分类。

### 1.3 纳管对象的三种类型

| 类型 | 说明 | OpsGaurd 能力 | 举例 |
|---|---|---|---|
| `swarm-service` | swarm 编排的服务 | 部署/扩缩容/重启/日志/监控 | admin-server、opsguard_worker |
| `standalone-container` | `docker run` 的独立容器 | 查看/监控（不能编排） | r-nacos、grafana、nginxwebui |
| `host-service` | 宿主机原生服务（systemd/裸进程/端口） | 监控探活（不能查看容器） | 231 上的 AI 服务、宿主机 mysql |

> **"中间件"不是类型，是分类标签（category）。** 一个 swarm service 可以是中间件（redis swarm service），一个 standalone container 也可以是中间件（r-nacos），一个 host-service 也可以是中间件（裸跑 mysql）。category 由配置声明，不靠探测。

## 二、纳管清单模型（Inventory）

### 2.1 数据结构

纳管清单存在**集群记录**里（`store.Cluster` 新增 `Inventory` 字段），随集群一起持久化：

```go
// store/cluster.go — Cluster 新增字段
type Cluster struct {
    // ... 现有字段 ...
    Inventory *InventoryConfig `json:"inventory,omitempty"`
}

// InventoryConfig 纳管清单：声明集群里要纳管的外部对象（非 OpsGaurd 部署的 swarm service）
type InventoryConfig struct {
    Items []InventoryItem `json:"items" yaml:"items"`
}

// InventoryItem 纳管对象声明
type InventoryItem struct {
    Name       string            `json:"name"      yaml:"name"`       // 显示名（唯一）
    Type       string            `json:"type"      yaml:"type"`       // standalone-container | host-service
    Ref        string            `json:"ref"      yaml:"ref"`        // standalone: 容器名; host-service: host（host:port 为兼容旧格式，端口并入 Ports）
    Node       string            `json:"node,omitempty" yaml:"node,omitempty"` // 所在节点 hostname（standalone 必填）
    Ports      []string          `json:"ports,omitempty" yaml:"ports,omitempty"` // 探活端口列表（多端口聚合探活；standalone 未声明时取容器实况端口）
    Category   string            `json:"category"  yaml:"category"`   // middleware | business | infra | ...
    Desc       string            `json:"desc,omitempty" yaml:"desc,omitempty"`
    // Monitoring 复用 store.Monitoring schema（PortCheck/HTTPCheck/LogCheck/ResourceThreshold），
    // 与 swarm service 的 config.Monitoring / AlertRule 统一契约——不另造监控配置类型。
    Monitoring *store.Monitoring `json:"monitoring,omitempty" yaml:"monitoring,omitempty"`
}
```

> `swarm-service` 不在 inventory 里声明——它们由 `config.Service` 部署配置声明（已含 name/labels.category/monitoring）。inventory 只管"OpsGaurd 没部署但要纳管"的外部对象。

### 2.2 YAML 格式

```yaml
inventory:
  items:
    # r-nacos：docker run 部署的注册/配置中心
    - name: r-nacos
      type: standalone-container
      ref: rnacos                    # docker ps 里的容器名
      node: NXYJGLT-YJ-b-1           # 所在节点 hostname（必须，否则不知道去哪个节点找）
      category: middleware
      desc: 注册/配置中心（r-nacos v0.8.6，OAuth2 对接 OpsGaurd IdP）
      monitoring:
        portChecks:
          - port: 8848               # OpenAPI
          - port: 9848               # gRPC
          - port: 10848              # 控制台
        httpChecks:
          - url: http://localhost:8848/nacos/v1/console/health/readiness
            expectedStatus: [200]

    # grafana：232 上的监控面板
    - name: grafana
      type: standalone-container
      ref: grafana
      node: NXYJGLT-YJ-b-1
      category: middleware
      monitoring:
        portChecks:
          - port: 3000

    # AI-Chat：231 上宿主机裸跑的 AI 服务（不是容器）
    - name: AI-Chat
      type: host-service
      ref: 10.60.171.231:3000        # host:port
      node: NXYJGLT-YJ-5
      category: middleware
      monitoring:
        portChecks:
          - port: 3000
            host: 10.60.171.231

    # 宿主机 SSH（infra 类）
    - name: sshd
      type: host-service
      ref: 0.0.0.0:22
      category: infra
      monitoring:
        portChecks:
          - port: 22
```

> **Ports 字段（2026-08 后新增，2026-08-21 复核补记）**：探活端口提升为 `ports` 一等字段，支持一个对象**多端口聚合探活**——standalone 未声明时自动取容器实况端口；host-service 的 `ref` 现推荐只写 `host`（旧 `host:port` 格式兼容，端口并入 `ports`）。

### 2.3 label-input 表单方式

同一份配置也支持表单逐条编辑（对不熟悉 yaml 的用户友好）：

| 表单字段 | 对应 yaml | 说明 |
|---|---|---|
| 名称 | name | 唯一标识 |
| 类型 | type | 下拉：独立容器 / 宿主机服务 |
| 引用 | ref | 容器名 或 host:port |
| 所在节点 | node | 下拉（从集群节点列表取） |
| 分类 | category | 下拉：中间件 / 业务 / 基础设施 |
| 描述 | desc | 自由文本 |
| 监控 | monitoring | 嵌套表单：端口检查 / HTTP 检查（可多条） |

前端用 `el-dialog` + 动态表单（参照现有部署服务的表单模式），同时提供"编辑 YAML"切换（`el-input type=textarea` + yaml 解析校验）。

## 三、config.Service 加 securityOpt + pidMode

### 3.1 动机

- **securityOpt**：r-nacos（Rust）需要 `seccomp=unconfined`，否则 panic。当前 `docker service create` 不支持 `--security-opt`，导致 r-nacos 只能 `docker run`（不在 swarm 管理范围）。加完后 r-nacos 可走 OpsGaurd 编排部署。
- **pidMode**：worker 容器加 `pid: host` 后能看到宿主机真实进程（当前"宿主机进程"只有 worker 自己，因为 PID namespace 隔离）。

### 3.2 改动

```go
// Worker/internal/config/config.go — Service 新增字段
type Service struct {
    // ... 现有字段 ...
    SecurityOpt []string `yaml:"securityOpt,omitempty" json:"securityOpt,omitempty"`
    PidMode     string   `yaml:"pidMode,omitempty"   json:"pidMode,omitempty"`   // "" | "host"
}

// Worker/internal/docker/types.go — ContainerSpec 新增字段
type ContainerSpec struct {
    // ... 现有字段 ...
    Privileges *Privileges `json:"Privileges,omitempty"` // 内含 SecurityOpt（Engine API 要求嵌套，顶层裸 SecurityOpt 会被拒绝）
    PidMode    string      `json:"PidMode,omitempty"`
}

// Worker/internal/orchestrator/translator.go — Translate 里补映射（注意嵌套）
spec.ContainerSpec.Privileges.SecurityOpt = cfg.Service.SecurityOpt
spec.ContainerSpec.PidMode = cfg.Service.PidMode
```

### 3.3 部署 YAML 示例

```yaml
# r-nacos 走 swarm 编排（securityOpt 解锁 Rust tokio 线程）
service:
  name: rnacos
  image: qingpan/rnacos:stable
  securityOpt: ["seccomp=unconfined"]
  # ... 其余配置

# worker 加 pidMode: host（宿主机进程可见）
service:
  name: opsguard_worker
  image: opsguard-worker:1.0.8
  pidMode: host
  # ...
```

## 三补、监控与告警的配置驱动

### 3补.1 原则

**监控对象、检查项、告警规则、通知策略——全部由配置声明，不自动探测、不自动告警。**

- **不自动监控**：只有纳管清单里声明的对象（swarm service 的部署配置 `config.Monitoring` + inventory item 的 `Monitoring`）才被监控。不在清单里的不监控。
- **不自动告警**：告警由 `AlertRule`（cluster + target + Monitoring + 阈值）配置驱动，不根据异常自动生成规则。
- **不自动通知**：通知策略由 `NotifyPolicy`（level + channelIDs + receivers）配置驱动。

### 3补.2 统一 schema（复用现有，不另造）

监控配置统一用 `store.Monitoring`（`OpsGaurdWeb/server/internal/store/notify.go:86`），与 Worker 的 `config.Monitoring` JSON 契约一致：

| 检查类型 | 字段 | 适用对象 | 执行路径 |
|---|---|---|---|
| `PortCheck` | port/protocol/interval/timeout/retries | swarm-service / standalone / host-service | Worker `monitor/portcheck.go`（swarm）或 `NodeClient.CheckPort`（节点级） |
| `HTTPCheck` | url/method/headers/expectedStatus/expectedBody | 同上 | Worker `monitor/httpcheck.go` 或 `NodeClient.CheckHTTP` |
| `LogCheck` | pattern/level/ignore/action | swarm-service / standalone | Worker `monitor/logcheck.go`（需容器日志流） |
| `ResourceThreshold` | metric(cpu\|memory)/threshold/action | swarm-service / standalone | Worker `monitor/rescheck.go`（容器 stats） |

> host-service 不支持 LogCheck/ResourceThreshold（无容器）；PortCheck/HTTPCheck 通过 `NodeClient` 探活。
>
> **当前执行状态（2026-08）**：纳管对象的 PortCheck/HTTPCheck/容器存活由 server 侧 `invmonitor` 执行（见 §3补.4）；
> standalone 的 LogCheck/ResourceThreshold 暂只存配置不执行（需容器日志流/stats 通路，后续扩展）。

### 3补.3 监控对象的三种来源（全部配置声明）

| 来源 | 监控配置在哪 | 何时声明 |
|---|---|---|
| swarm service | `config.Service.Monitoring`（部署 YAML） | 部署时 |
| standalone container | `InventoryItem.Monitoring`（纳管清单） | 接入/编辑纳管时 |
| host-service | `InventoryItem.Monitoring`（纳管清单） | 接入/编辑纳管时 |

### 3补.4 告警与通知（已有体系，纳管对象监控已落地执行）

`AlertRule`（`store/notify.go`）= `{cluster, service, Monitoring, updated_at}`：
- `service` 字段语义为"纳管对象 name"（swarm service name 或 inventory item name）。
- inventory item 的告警规则同样以 `AlertRule` 持久化（cluster + item_name + Monitoring），走同一套告警/通知链路。
- `NotifyPolicy`（level + channelIDs + receivers）不变，按 level 匹配告警。

**执行路径（已实现，2026-08）**：
- **swarm service**：规则「下发」→ `alertrule.Apply` 合并 monitoring 进服务 config → Worker Update（Worker `monitor.Manager` 常驻循环执行）。
- **inventory item**：规则「下发」→ 合并进 `InventoryItem.Monitoring` 落库 → server 侧 `internal/invmonitor` 调度器周期探测（每 30s 一轮，按各检查 interval 节流），探测原语复用 `workerproxy.CheckPort / CheckHTTP / NodeContainers`——与巡检（patrol）同一执行路径，**Worker 零改动**。
  - host-service：portChecks → CheckPort（目标 host 取 ref）；httpChecks → CheckHTTP（URL 按声明）。
  - standalone-container：容器存活（NodeContainers 按 ref 匹配，非 running/消失 → `container_down`）；portChecks → 对节点地址探测；httpChecks → 按声明 URL 探测。
  - 状态翻转才发事件：失败 → `port_down`/`http_unhealthy`/`container_down`（error）；恢复 → `recovered`（info）自动关闭告警。RPC 失败（节点不可达）不翻转、仅节流。
  - 纳管对象的 resourceThresholds / logChecks 本期**只存配置不执行**（UI 可见，后续扩展）。
- **双向同步**：纳管清单保存时，带 monitoring 的条目自动 upsert 同名 AlertRule——规则列表始终是全集群监控配置的统一视图；清单条目删除时同步删除内容一致的规则。
  - 幽灵告警治理（2026-08 补充，74a542e）：检查配置变更/移除时补发恢复事件；事件 ID 加序号防低分辨率时钟同 tick 去重。
- **统一入口**：集群详情页「告警规则」tab（管理本集群全部规则）；系统设置不再承载规则管理。

```yaml
# 告警规则示例（cluster + service + monitoring；注意字段名为 service 而非早期草稿的 target）
alertRules:
  - cluster: nxyj-cluster
    service: r-nacos              # inventory item name（或 swarm service name）
    monitoring:
      enabled: true
      portChecks:
        - port: "8848"
          interval: 30s
        - port: "9848"
          interval: 30s
      httpChecks:
        - url: http://10.60.171.249:8848/nacos/v1/console/health/readiness   # 写实际地址
          expectedStatus: [200]
          interval: 60s
  - cluster: nxyj-cluster
    service: admin-server          # swarm service name
    monitoring:
      enabled: true
      resourceThresholds:
        - metric: cpu
          threshold: 80
          action: alert

# 通知渠道类型以 store 为准：feishu | webhook（sms 预留经代理）；
# 钉钉/企业微信用 webhook 类型对接其机器人地址（早期草稿的 dingtalk-1/email-1 类型未实现）。
notifyPolicies:
  - level: error
    channelIDs: [feishu-1]
  - level: warn
    channelIDs: [feishu-1]
```

### 3补.5 巡检（patrol）与监控的关系

patrol（`server/internal/patrol`）是**按配置调度的主动探活**（Check.Type: resource/health/port/http/process/flow）。与监控的关系：
- patrol 配置（PatrolCheck）也是配置驱动——不自动巡检所有对象，只巡检配置里声明的。
- patrol 的 target 可以是纳管清单里的对象（inventory item name 或 swarm service name）。
- patrol 产生的异常走告警链路（AlertRule → NotifyPolicy）。

> 巡检和监控共用 `NodeClient.CheckPort/CheckHTTP/CheckFlow` 执行路径，区别在调度方式（monitor 是 Worker 常驻循环，patrol 是 server 定时触发）。

## 四、数据流（server 按 type 分发）

```
前端请求 GET /api/v1/clusters/:name/inventory
  → server 读 cluster.Inventory 配置
  → 对每个 item 按 type 分发查询：
      standalone-container:
        → NodeClient(node).Containers() 找 ref 匹配的容器
        → 返回容器详情（name/image/state/ports）+ 配置的 category
      host-service:
        → NodeClient(node).CheckPort(host, port)
        → 返回探活结果（ok/latency）+ 配置的 category
      （swarm-service 不在 inventory 里，由 ListWorkloads 单独查）
  → 合并 swarm services（ListWorkloads，category 来自 labels）+ inventory items
  → 按 category 分组返回
```

### 4.1 新增 API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/clusters/:name/inventory` | 获取纳管清单（合并 swarm services + inventory items，按 category 分组） |
| PUT | `/api/v1/clusters/:name/inventory` | 更新纳管清单（整体替换 yaml/json） |

### 4.2 前端展示变化

| 标签页 | 现状 | 改后 |
|---|---|---|
| 容器与服务 | swarm services | **已改名「服务 (N)」并合并展示所有纳管对象**（swarm service + standalone 容器 + 裸进程），带"来源/分类"列，不再是纯 swarm 视图 |
| 中间件 | swarm services 里 category=middleware 的 | **swarm middleware + inventory 里 category=middleware 的 standalone/host-service**，用一列标记来源（swarm/standalone/host）+ 所在节点 |
| 节点 → 容器 tab | 全量容器（已做） | 不变（节点级全量视图） |
| 节点 → 进程 tab | 只有 worker 自己 | worker 加 pidMode:host 后能看到宿主机进程（实现为 top-N 截断：`limit` 默认 100 上限 500 + `top=cpu|mem` + `filter`，非 page/pageSize 分页） |

## 七、风险与取舍

| 项 | 说明 | 处理 |
|---|---|---|
| inventory 存在哪 | 集群记录 vs 独立配置 | 存集群记录（`store.Cluster.Inventory`），随集群一起 CRUD，不引入额外存储 |
| swarm service 是否也进 inventory | 否——swarm service 由 config.Service 部署配置声明，不重复 | inventory 只管外部对象；swarm service 的分类靠 `labels.category` |
| standalone 容器的节点查找 | 配置里必填 node（hostname），避免遍历全节点 | 如果 node 填错，查询返回 not-found，UI 标红 |
| host-service 的探活频率 | 走 patrol（巡检）调度，不实时 | 复用现有 patrol 的 port/http check |
| securityOpt 的安全风险 | `seccomp=unconfined` 放宽容器限制 | 仅用于确有需要的中间件（Rust tokio），配置时提示风险 |
| pidMode=host 的安全风险 | worker 能看到宿主机所有进程 | 仅 worker 使用，且有鉴权保护；其他服务不加 pid=host |
| 配置向后兼容 | 现有集群无 inventory 字段 | `Inventory *InventoryConfig` 指针类型，nil = 空清单，旧记录不受影响 |
| 表单 vs YAML | 两种输入方式要保持一致 | 表单↔YAML 双向转换（前端 yaml.parse + stringify），统一校验 |

## 九、排障（AiNexus）链路的纳管对象支持（2026-09-09 已实施）

### 9.1 问题

纳管对象的声明只存在服务端（`store.Cluster.Inventory`），Worker 不感知；而 AiNexus 深度排查的三条入口（页面 investigate、chat 带 alert_id 种子、管理端 MCP `investigation_start`）的采证与提示词全部 swarm 中心：

- **采证注入为空**：事件走 Worker `ListEvents`（纳管对象事件由 invmonitor 直写服务端、不过 Worker）；日志走 `docker service logs`（非 swarm 服务直接报错）。
- **工具面落空**：`list_services/get_service/get_service_logs/get_resource_usage/exec_in_container` 全部以 swarm service 为对象，standalone 容器与宿主机服务连枚举都不可见；`check_port/check_http/list_host_processes` 原语在集群节点侧可用，但缺少"该探谁、探哪个节点哪个端口"的纳管元数据。
- **提示词误导**：system 硬编码"Docker Swarm 集群故障排查"，对象 not found 时模型易误判为已删除。

### 9.2 原则：管理面出"地图"，集群面出"实弹"

采证动作（探活/容器/进程）必须落在**目标集群的节点**上执行（管理端不在集群网内，探测不可达也不真实——invmonitor 与管理端 probe_* 同此约束）；管理面只注入**声明性上下文**（纳管声明、监控规则定义、服务端事件历史）。Agent 的 `cluster:<name>` 工具 scoping 保证它只用目标集群 Worker 的工具采证。

### 9.4 遗留与备注

- **standalone 容器日志通路（第三步，未做）**：nodeagent `logs` 只实现 `docker service logs`，无 `docker logs` 级别的按容器取日志（需 nodeagent → gRPC → MCP 三层贯通）；此前排查可临时用 `exec_host_command docker logs`（需 confirm，受命令策略约束）。
- **host-service 无日志概念**（宿主进程），排障证据 = 探活结果 + 进程列表 + 服务端事件。
- 管理端 MCP `cluster_events` 工具描述称"server-side store"，实现实际走 Worker `ListEvents`——描述与实现不一致，待修正（纳管对象事件在 Worker 侧查不到）。
