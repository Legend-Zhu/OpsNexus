# 用户管理与集群负责人告警通知方案（含短信渠道）

> 版本：v2.1（设计稿，未实施）
> 日期：2026-09-08
> 关联：docs/OpsGaurdWeb-设计方案.md、docs/告警规则删除级联停止监控方案.md、deploy/internet-proxy/main.go
> 变更：v2.0 按评审意见调整为**渠道网关化架构**——渠道适配全部下沉通知网关，管理端不适配任何渠道；v2.1 补充**网关管理面**——网关及其渠道在管理端通知中心统一管理（配置存网关侧、凭据不落内网）；v1.0 为管理端保留渲染的初稿。

## 一、背景与需求

### 1.1 需求描述

1. **用户管理增强**：用户可配置联系方式（手机号、飞书身份），作为告警通知的接收基础。
2. **集群负责人**：每个集群可配置一个或多个负责人；集群告警定向通知到人。
3. **飞书多形态触达**：告警既走群机器人，也能**私聊负责人**，紧急告警**应用内加急**（buzz）。
4. **短信渠道**：供应商接口未确定，但**功能要先行**——管理端全链路先打通，真实供应商留可插拔实现点。
5. **架构诉求（评审意见）**：
   - 渠道适配整体收敛到网关一侧，**管理端不出现任何渠道专属代码**——新增钉钉、企微等渠道时管理端零改动；
   - **渠道与网关本身要在管理端通知中心统一管理**——运维不登互联网服务器改环境变量，渠道的增删改、测试、启停都在通知中心完成。

### 1.2 现状盘点

| 领域 | 现状 | 位置 |
|---|---|---|
| 用户模型 | `store.User`（ID/Username/Role/Enabled/Email/DisplayName），**无手机号、无飞书身份** | `server/internal/store/notify.go:169` |
| 用户 API | 列表/创建/改密/重置密码，**无资料更新接口** | `server/internal/api/system.go:367-468`、`router.go:215` |
| 集群模型 | `store.Cluster`（Name/ProjectID/Desc/Status…），**无负责人字段** | `server/internal/store/cluster.go:24` |
| 通知策略 | `NotifyPolicy` 只有**全局按级别**（info/warn/error → 渠道列表）一个维度；**无集群维度路由** | `server/internal/store/notify.go:49`、`notify/notify.go:189 NotifyAlert` |
| 渠道适配（管理端） | **管理端深度适配渠道**：飞书卡片构造（alertCard，:378）、post 富文本渲染（reportPost 全套 Markdown 解析，:524）、事件/级别中文标签（:416,:437）等约 300 行渠道渲染代码；`send()` 按渠道类型 switch | `server/internal/notify/notify.go` |
| 渠道管理 | 渠道 CRUD 在通知中心（type + config 存管理端），但飞书应用凭据、加急对象、短信实现全在网关环境变量——**同一渠道的配置劈在两处，改网关侧要登机器** | `deploy/internet-proxy/main.go:54-103` |
| 加急 | internet-proxy `/urgent` 已实现「应用发群消息 + 应用内加急」，但加急对象是**环境变量写死的值班用户列表** | `deploy/internet-proxy/main.go:252,317` |
| 短信 | `ChannelSMS` 类型已预留（强制 via_proxy），管理端无发送分支，代理侧返回 501「sms 未实现」 | `store/notify.go:29`、`deploy/internet-proxy/main.go:348-350` |
| 告警触发 | ingest 新告警 / 巡检 / 认领 / 恢复四处统一调 `NotifyAlert(ctx, alert, subject)`，签名统一 | `ingest/ingest.go:125`、`patrol/service.go:837`、`api/monitor.go:61,83` |

### 1.3 差距结论

- **到「人」的链路完全缺失**：没有「用户 → 飞书私聊 / 手机号」的解析与发送。
- **集群维度路由缺失**：`NotifyAlert` 只看级别，不看集群负责人。
- **渠道知识与渠道配置错位**：渲染逻辑在管理端、凭据在网关 env、渠道记录又在管理端——三处割裂，加渠道要动两个部署体、登一次互联网服务器。
- **短信链路两头都是占位**：是「功能先行」的理想切入点。

## 二、设计原则

1. **管理端渠道无关（第一原则）**：管理端只产出「领域消息 + 投递意图」，不做渠道格式渲染、不含渠道 SDK 知识。渲染、凭据、供应商 SDK 全部在**通知网关**。新增渠道 = 网关加一个 adapter + 通知中心加一个表单模板，管理端 Go 代码零改动。
2. **通知中心是唯一管理入口**：网关注册、渠道（网关侧 adapter 实例）增删改、测试发送、启停，全部经通知中心完成；网关自身**无人肉运维**。实现方式：网关提供管理面 API，通知中心做代理管理界面——**配置存网关侧、凭据不落内网存储**（既定铁律不放松，管理面只是统一入口，不是把凭据搬进内网库）。
3. **告警触发点零改动**：`NotifyAlert` 签名不变，ingest/巡检/认领/恢复四个调用点不动。
4. **协议向前兼容、可灰度**：网关 v2 与 v1 端点并存一个版本周期；管理端切换以配置开关保护，无锁定部署顺序。
5. **失败隔离、逐条记录**：逐投递意图独立发送、逐目标写发送记录，单点失败不扩散。
6. **加急与高级别触达防滥用**：私聊/加急/短信均由级别阈值门控，加急一期仅应用内（免费），显式开启才生效。

## 三、总体架构

### 3.1 分层与职责边界

```
管理端（内网，OpsGaurdWeb server）                     通知网关 notify-gateway（互联网侧，internet-proxy 演进）
┌────────────────────────────────────┐              ┌──────────────────────────────────────────┐
│ 【管理面·通知中心统一入口】            │  管理 API    │ 【管理面】adapter 实例 CRUD + 测试 + 健康   │
│  网关注册(URL+Token) / 渠道管理 /     │ ──────────→ │  配置持久化 adapters.json（凭据只存这里）    │
│  配置代理读写（凭据掩码，不落内网库）    │  /v2/admin  │ 【数据面】adapter 注册表（唯一渠道实现点）：  │
│ 【业务面】                          │              │  ├ feishu_webhook  群机器人（加签/卡片）    │
│  全局级别策略 + 集群策略（负责人/级别）  │  发送协议    │  ├ feishu_group    应用群发 + 加急        │
│  负责人 → open_id/手机号 解析         │ ──────────→ │  ├ feishu_dm       应用私聊 + 加急        │
│  领域消息（kind+Alert+markdown）      │  /v2/notify │  ├ webhook         通用 JSON POST（白名单）│
│  投递意图（adapter_id + 接收地址）     │              │  ├ sms             smsSender 驱动接口     │
│  发送记录（按 results 逐目标落库）     │              │  └ （钉钉/企微… 以后只加这里）              │
└────────────────────────────────────┘              │ 消息渲染：卡片/post/markdown 降级           │
                                                    │ 凭据持有：app secret / sms 密钥 / webhook   │
                                                    └──────────────────────────────────────────┘
```

**关键转移**：

- 管理端现有渲染代码（`alertCard` :378、`reportPost` :524、`eventTypeLabel`/`levelLabel` :416,:437，约 300 行）**删除、移入网关** feishu adapter；`send()` 的渠道 switch 消失。
- 渠道配置从「管理端存 config + 网关存 env」两处割裂，收敛为**网关侧 adapter 实例一份**；通知中心经管理面 API 远程管理它。

### 3.2 管理面与数据面分离（网关内）

- **管理面** `/v2/admin/*`：adapter 实例 CRUD、飞书应用凭据配置、webhook 白名单、逐 adapter 测试发送、健康清单。Bearer Token 鉴权（`GATEWAY_ADMIN_TOKEN`，与通知中心注册时配对）。
- **数据面** `/v2/notify`：投递请求按 `adapter_id` 引用管理面配置，**消息里不传凭据**（对比 v1：config 随消息走）。
- 配置持久化：网关侧 `adapters.json`（原子写：临时文件+rename）；**首启无此文件时从环境变量导入**（FEISHU_WEBHOOK/FEISHU_APP_ID/… 合成初始实例），存量部署零配置升级，v1 端点继续读同一份配置。

### 3.3 管理端保留什么、移除什么

| 保留（业务/管理面入口） | 移除（渠道域） |
|---|---|
| 网关注册 CRUD（URL+Token，token 脱敏展示） | `validateChannelConfig` 按类型校验（改由网关测试发送验证） |
| 渠道管理 UI（代理读写网关配置，掩码展示） | 飞书卡片与 post 渲染全套 |
| 全局策略 / 集群策略、负责人 → open_id/手机号解析 | 渠道类型 switch 发送分支、渠道降级规则 |
| 领域消息构造、投递意图、发送记录 | 渠道 config 的本地存储（迁至网关） |

说明：**前端**仍按 adapter 类型渲染参数表单（配置 UX，不是后端适配）；管理端后端对网关配置全程不解释、凭据只透传不落库。

### 3.4 部署形态

- **网关是角色不是固定实例**：渠道记录携带 `gateway_id`，支持多个网关实例。
- 互联网侧实例（现有 internet-proxy 所在机）：承载 feishu_webhook / feishu_group / feishu_dm / sms 等需公网出网的 adapter。
- 内网侧实例（可选，未来需要时同一二进制另起）：承载指向内网系统的 webhook adapter。当前不需要部署。
- 网闸可用性成为全部通知的依赖（现状经代理的渠道本就如此）。缓解：网关 `/healthz` 纳入巡检探活、通知中心网关 Tab 显示健康态、发送失败有记录可查（§十）。

## 四、网关协议 v2

### 4.1 数据面：`POST {gateway_url}/v2/notify`

```json
{
  "trace_id": "nr-1757...",
  "message": {
    "kind": "alert",                  // alert | recover | ack | report | text | test
    "level": "error",                 // info | warn | error（text/test 可空）
    "alert": { },                     // kind=alert|recover|ack 时必填：store.Alert 原样 JSON
    "subject": "[prod/redis] 资源超限：cpu 98%",
    "markdown": ""                    // kind=report|text 时正文（markdown）
  },
  "delivery": [
    { "adapter": "feishu_webhook", "adapter_id": "ad-101" },
    { "adapter": "feishu_dm",      "to": [ { "open_id": "ou_x", "urgent_app": true } ] },
    { "adapter": "sms",            "adapter_id": "ad-102", "to": [ "13800138000" ] }
  ]
}
```

响应（逐目标结果）：

```json
{ "ok": true,
  "results": [
    { "adapter": "feishu_dm", "to": "ou_x", "ok": true, "message_id": "om_x", "urgent": true },
    { "adapter": "sms", "to": "13800138000", "ok": false, "error": "sms 供应商未接入" }
  ] }
```

设计要点：

- **`adapter_id` 引用代替 config 内联**：渠道实配置（webhook_url、chat_id、供应商密钥）由网关按 id 从 adapters.json 取——消息不携带凭据，配置变更即时生效，且与「通知中心管理」同源。adapter_id 不存在/禁用 → 该目标 result 明确报错，其余目标不受影响。
- **`message` 是领域模型不是渠道格式**：`alert` 直接序列化 `store.Alert`，卡片样式由网关 feishu adapter 决定；webhook adapter 收 `{title, alert}`（与现状直连负载一致）；sms 取纯文本降级。领域对象进、渠道格式出。
- **`markdown` 是渠道无关内容形态**：巡检报告直传 markdown，post 渲染（现 `reportPost`）整体在网关；webhook 收 `{title, content}`，sms 收纯文本。
- **feishu_dm 无 adapter_id**：使用网关级飞书应用凭据（管理面配置的 `app`，单实例），open_id/加急意图随消息携带。
- 网关保证任一目标失败不影响其余目标；全部失败才返回非 200。管理端按 `results` 逐目标写发送记录——记录粒度天然对齐到「人/号」。
- **发送规则**：按 `gateway_id` 分组投递意图，同网关同 adapter 合并请求（多位负责人一次 feishu_dm）；超时 10s（网关预算 8s，现状不变）；不重试（边沿触发，状态再变化自然再通知）。

### 4.2 管理面：`/v2/admin/*`（网关新增）

| 端点 | 说明 |
|---|---|
| `GET /v2/admin/config` | 网关配置总览：app 凭据掩码（has_app_secret）、adapter 实例清单（凭据掩码）、白名单、健康状态 |
| `PUT /v2/admin/app` | 飞书应用凭据（app_id/app_secret/默认群 chat_id）；secret 留空 = 保持现值 |
| `GET /v2/admin/adapters` | adapter 实例列表（id/type/name/enabled，凭据掩码） |
| `PUT /v2/admin/adapters/:id` | 创建/更新实例（type/name/config/enabled；凭据留空 = 保持现值；改 type 禁止——新建实例） |
| `DELETE /v2/admin/adapters/:id` | 删除实例 |
| `POST /v2/admin/adapters/:id/test` | 单实例测试发送（发送预置文案，返回结果） |

- **鉴权**：Bearer `GATEWAY_ADMIN_TOKEN`（随机 32 字节，网关 env 引导生成，通知中心注册网关时填入；恒定时间比较）。
- **凭据掩码**：所有 GET 不回传明文凭据，返回 `has_secret` 布尔（沿用 `Cluster.HasToken` 的既有模式）；PUT 空值保持——通知中心编辑表单才能「不改密钥只改地址」。
- **持久化**：adapters.json 原子写；env 导入仅发生一次（文件缺失时）。

### 4.3 v1 兼容与下线

- 网关新增 v2，**保留** `/notify`、`/urgent`（v1）不动——老管理端不受影响；v1 继续读 env 导入后的配置。
- 管理端切 v2 后一个版本周期，v1 端点下线。
- **部署顺序无强制**：先升网关（无感知）、再升管理端；`notify.protocol=v1|v2`（默认 v2）保护一个版本周期，回滚改配置。

## 五、数据模型

### 5.1 User 扩展（`store/notify.go`）

```go
type User struct {
    // ...现有字段不变...
    Phone        string `json:"phone,omitempty"`         // 手机号（短信收件人）
    FeishuOpenID string `json:"feishu_open_id,omitempty"` // 飞书 open_id（ou_ 开头）
}
```

- 飞书身份用 **open_id**（应用可见范围内可直接作 receive_id 与加急标识，不依赖通讯录 user_id 权限）。
- 格式校验：手机号 `^(\+86)?1[3-9]\d{9}$`、open_id `^ou_[0-9a-zA-Z]{20,}$`（宽松前缀校验）。
- 全部 `omitempty`，旧记录反序列化无影响。SSO 用户资料一期 admin 手工补全（§十三-9）。

### 5.2 Cluster 扩展：负责人（`store/cluster.go`）

```go
type Cluster struct {
    // ...现有字段不变...
    OwnerIDs []string `json:"owner_ids,omitempty"` // store.User.ID（稳定标识，同 IdP GetUserID 先例）
}
```

- 负责人属「集群资料」放 Cluster；通知行为配置属「通知域」独立存储（5.4），生命周期解耦。
- 写入校验：OwnerIDs 必须指向存在且 `Enabled` 的用户；发送时二次过滤（离职兜底）。

### 5.3 新增 NotifyGateway：网关注册表（`store/notify.go`）

```go
// key: notify/gateway/<id>
type NotifyGateway struct {
    ID        string    `json:"id"`   // gw-<unixnano>
    Name      string    `json:"name"`
    URL       string    `json:"url"`  // 网关基址（如 http://10.60.x.x:50378）
    Token     string    `json:"token,omitempty"` // 管理面 Bearer；落盘持久化，对外经 Public() 抹除（HasToken）
    Enabled   bool      `json:"enabled"`
    CreatedAt time.Time `json:"created_at"`
    UpdatedAt time.Time `json:"updated_at,omitempty"`
}
```

- 通知中心「网关」Tab 管理对象；保存时调 `/v2/admin/config` 做连通性与 Token 验证。
- 升级自动迁移：存量 via_proxy 渠道按 ProxyURL 去重，自动登记为「默认网关」（Token 空 → UI 标「待补 Token」）。

### 5.4 新增 ClusterNotifyPolicy（`store/notify.go`）

```go
// key: notify/clusterpolicy/<cluster>
type ClusterNotifyPolicy struct {
    Cluster string `json:"cluster"`
    // DirectLevel 负责人飞书私聊起始级别：""=不私聊；info|warn|error=达到及以上。
    DirectLevel string `json:"direct_level,omitempty"`
    // UrgentLevel 应用内加急起始级别：""=不加急。前提：DirectLevel 非空且 UrgentLevel ≥ DirectLevel。
    UrgentLevel string `json:"urgent_level,omitempty"`
    // SMSLevel 负责人短信起始级别：""=不发；SMSChannelID 为空时同样不生效。
    SMSLevel string `json:"sms_level,omitempty"`
    // SMSChannelID 短信渠道 ID（type=sms 的渠道记录）。
    SMSChannelID string `json:"sms_channel_id,omitempty"`
    // ExtraChannelIDs 集群专属渠道（如该集群自己的群机器人），任意级别随全局策略并发。
    ExtraChannelIDs []string `json:"extra_channel_ids,omitempty"`
    UpdatedAt time.Time `json:"updated_at"`
}
```

- 三个 Level ∈ {"", "info", "warn", "error"}，比较序 info < warn < error；校验 `UrgentLevel >= DirectLevel`、渠道引用存在。
- 全局 `NotifyPolicy` **保持不变**，继续承担「告警进群」默认路由；集群策略是叠加项，存量部署不配则行为与今天一致。
- 删除集群时级联删除策略（复用告警规则级联清理挂载点）。
- 负责人私聊（feishu_dm）不占渠道记录（无渠道参数，应用凭据在网关级）；其网关地址 = 集群策略新增字段 `DMGatewayID`（空则回退全局设置 `notify.default_gateway_id`）。

### 5.5 NotifyChannel：渠道记录变为「网关实例引用」

```go
// NotifyChannel 渠道 = 网关侧 adapter 实例的通讯录条目（策略引用的稳定句柄）。
type NotifyChannel struct {
    ID        string `json:"id"`
    Name      string `json:"name"`
    Type      string `json:"type"`     // adapter 名：feishu_webhook|feishu_group|webhook|sms（展示/表单路由用）
    GatewayID string `json:"gateway_id"`
    AdapterID string `json:"adapter_id"` // 网关侧实例 id（ad-*）；实配置存网关，这里不存 config
    Enabled   bool   `json:"enabled"`
    // Synced 标记本地记录与网关实例的一致状态（网关不可达创建时为 false，UI 标「未同步」）。
    Synced    bool      `json:"synced"`
    CreatedAt time.Time `json:"created_at"`
}
```

- **config 不再存管理端**：创建/编辑渠道 = 通知中心表单 → 管理面 API 写网关实例 → 本地写引用记录（先网关后本地，网关成功则本地必成，无两阶段问题；网关不可达时本地记 `Synced=false` 可重试）。
- 存量兼容：旧 `Config`/`ViaProxy`/`ProxyURL` 字段读取保留一个版本周期；升级迁移见 §十一。
- 全局 `NotifyPolicy`/集群策略引用的 ChannelIDs 语义不变——策略仍引用本地渠道记录，删除网关实例时若被渠道引用则拒绝。

### 5.6 NotifyRecord 扩展


## 六、adapter 设计（网关侧）

```go
// adapter 渠道适配器：v2 消息 → 渠道格式 → 发送。唯一允许出现渠道知识的地方。
type adapter interface {
    Name() string
    Deliver(ctx context.Context, cfg json.RawMessage, msg *Message, d *Delivery) []Result
}
// 实例配置由管理面维护、数据面按 adapter_id 注入 cfg。
var adapters = map[string]adapter{
    "feishu_webhook": newFeishuWebhookAdapter(), // 复用现有 sendWebhook（加签）
    "feishu_group":   newFeishuGroupAdapter(),   // 复用现有 sendAppMessage + urgentApp
    "feishu_dm":      newFeishuDMAdapter(),       // 新增（网关级 app 凭据）
    "webhook":        newWebhookAdapter(),        // 新增（白名单）
    "sms":            newSMSAdapter(),            // 新增（驱动接口）
}
```

未注册 adapter 名或未配置实例 → 该目标 result 明确报错，其余不受影响——网关先于管理端升级时天然前向兼容新渠道。

### 6.1 feishu_webhook（群机器人）

- 现有 `sendWebhook`（:137，自动加签）+ card/post 负载逻辑迁入；新增：从 `message.alert` 构造告警卡片（现管理端 `alertCard` 移入）、从 `markdown` 渲染 post（现 `reportPost` 移入）。中文标签（🔴 紧急等）随渲染一并移入。
- 实例配置：`{webhook_url, secret}`（secret 管理面掩码维护）。

### 6.2 feishu_group（应用群发 + 加急）

- 现有 `/urgent` 链路泛化：chat_id 来自实例配置（替代 env 写死）、加急目标来自 delivery `to`（open_id 列表，替代 `FEISHU_URGENT_USER_IDS` 静态列表；env 保留兼容 v1）。
- 实例配置：`{chat_id}`；依赖网关级 `app` 凭据，未配置时 result 明确报错。

### 6.3 feishu_dm（应用私聊 + 加急，新增）

- 应用身份按 open_id 私聊（`im/v1/messages, receive_id_type=open_id`），`urgent_app=true` 时对该 message 对该用户 PATCH urgent_app（`user_id_type=open_id`）。
- 逐目标独立：单人失败写该目标 result；加急失败不影响私聊 result（`urgent:false` + error）。
- 依赖网关级 `app`；权限新增 `im:message`（应用单聊）、`im:message.urgent`；应用可用范围须覆盖负责人。
- open_id 获取：一期 admin 在飞书后台查询后填入用户资料；二期可选网关按手机号反查（`contact/v3/users/batch_get_id`，开关式，需通讯录读权限），不阻塞一期。

### 6.4 webhook（通用 JSON）

- 负载与现状直连一致：`{title, alert}` / `{title, content}`，无渲染。实例配置 `{url, headers}`。
- **SSRF 防线**：网关在互联网侧不得成为任意 URL 跳板。`WEBHOOK_ALLOW_HOSTS` 白名单（管理面可编辑，默认空 = adapter 禁用，目标报明确错误）；内网目标由内网网关实例承载（§3.4）。存量 webhook 渠道迁移后需配白名单，写入部署手册。

### 6.5 sms（驱动接口，功能先行）

```go
// smsSender 短信供应商驱动。选型后新增文件（如 sms_aliyun.go）注册即可。
type smsSender interface {
    Name() string
    Send(ctx context.Context, phones []string, content string) error
}
// 实例配置含 provider 选择 + 供应商参数（密钥/签名/模板），管理面维护、掩码展示。
// provider=none（默认）：result 返回「短信供应商未接入」——与现状 501 等效，
// 但协议/路由/记录/测试全链路可验证。签名/模板拼装由驱动负责（报备属选型期事务）。
```

- 管理端不含任何供应商知识：发短信 = delivery 里 `{"adapter":"sms","adapter_id":...,"to":[...]}`。选型确定日 = 网关加一个 driver 文件，通知中心新建/改一个 sms 实例，管理端零改动。
- `/healthz` 与管理面 config 总览列出 adapter 清单与 sms driver 名，接入状态一眼可见。

## 七、告警通知链路改造（`notify/notify.go`）

`NotifyAlert` 签名不变，内部扩展为四步，产出投递意图后按网关分组发送：

```go
func (s *Service) NotifyAlert(ctx context.Context, alert *store.Alert, subject string) error {
    // ① 全局级别策略（现有）：渠道记录 → delivery{adapter=type, adapter_id, gateway}
    // ② 集群策略：ExtraChannelIDs 同上（任意级别）
    // ③ 集群策略：负责人私聊
    //    levelGE(level, DirectLevel) 且 DMGatewayID（或默认网关）可用 →
    //    过滤有 FeishuOpenID 且启用的负责人 → delivery{adapter:"feishu_dm",
    //    to:[{open_id, urgent_app: levelGE(level, UrgentLevel)}]}
    // ④ 集群策略：负责人短信
    //    levelGE(level, SMSLevel) 且 SMSChannelID 有效 →
    //    收集有 Phone 的负责人 → delivery{adapter:"sms", adapter_id, to:[...]}
    // 发送：按 gateway 分组 POST /v2/notify → 按 results 逐目标写 NotifyRecord
}
```

- **级别比较**：`levelGE(level, threshold)`，`""` 表示未启用。
- **失败隔离**：①—④ 互不影响，组内按 results 隔离；「至少一个目标成功 → `MarkAlertNotified`」语义保留。
- **通用发送（`Send`/`SendRich`，预算通知、巡检报告）**：改走 v2（kind=text/report + markdown），sms 渠道无收件人语义 → 跳过并记录。
- **告警风暴**：沿用边沿触发，不做频控；`EscalateConfig` 占位保留。
- patrol / 认领 / 恢复链路自动获得集群路由能力（都走 `NotifyAlert`，告警都带 Cluster）。

## 十、安全与边界

- **凭据边界（铁律不放松）**：app secret、短信密钥、webhook 加签密钥**只落网关侧 adapters.json**；管理端全程透传不落库、日志不打凭据、所有读取掩码（`has_secret`/`HasToken` 模式）。管理面调用方向为内网→互联网（既有网闸通路），Token 鉴权 + 恒定时间比较。
- **SSRF**：webhook adapter 白名单默认禁用；非白名单目标报明确错误；管理端不再直连任意 URL（现直连 webhook 场景并入网关）。
- **权限**：用户资料、负责人、集群策略、网关与渠道管理、测试发送全部 admin；`/users/options` 最小字段。
- **加急成本**：仅应用内加急（免费）；`UrgentLevel` 显式配置才触发；后续可加「每人每小时上限」频控（记录已具备统计基础）。
- **可用性**：网关与网闸成为全量通知依赖——`/healthz` 进巡检探活、通知中心网关 Tab 健康态、失败记录可查；网关无状态进程 + 单文件配置，可快速重启恢复。
- **审计**：全部发送经 `NotifyRecord`（含失败原因）；网关管理面访问留访问日志（现 withLog，路径级，不含 body 凭据）。

## 十三、开放问题与风险

| # | 问题 | 处理 |
|---|---|---|
| 1 | open_id 获取依赖手工查询 | 一期 admin 填写；二期网关按手机号反查（§6.3）。负责人人数少，可接受 |
| 2 | 短信供应商未选型 | 协议/链路先行；选型后仅网关加 driver。报备周期是关键路径，选型即启动 |
| 3 | 管理面 Token 泄露风险 | 仅内网可达（网闸单向映射）；Token 随机 32 字节、恒定时间比较、泄露即 env 重置；后续可换双向证书 |
| 4 | 网关成为全量通知单点 | `/healthz` 进巡检；失败记录可见；无状态进程 + 单文件配置可快速恢复；后续可双实例 |
| 5 | webhook adapter SSRF | 白名单默认禁用；内网目标走内网网关实例；存量渠道迁移需配白名单 |
| 6 | 飞书应用权限与可见范围 | im:message / im:message.urgent + 可用范围覆盖负责人；上线前 test 验证 |
| 7 | 渲染归网关后，通知样式改动需发网关 | 属预期（渠道展示归渠道域）；Alert 结构字段变更两端同步版本，v2 协议对未知字段忽略消化 |
| 8 | 加急/短信成本 | 级别阈值门控（建议 error 才开）；后续频控与用量展示 |
| 9 | 用户离职/禁用 | 发送时过滤 disabled；保存与发送两道校验 |
| 10 | 新集群重复配置策略 | 一期逐集群；集群多则二期加「全局默认集群策略」回退 |
| 11 | SSO 用户联系方式自动同步 | OIDC 标准不含手机号，需自定义 claim 或 SCIM，后续增强 |
| 12 | adapters.json 单文件损坏风险 | 原子写（tmp+rename）；启动时校验 JSON，非法则拒绝加载并保持 env 导入值；可选每日备份副本 |
