# 镜像拉取隧道中继方案（Tunnel Registry Relay）

> 目标：集群节点通过 **server↔worker 既有 gRPC 隧道**（网络策略仅 server→worker 可达）从管理端内嵌 OCI 仓库（`/v2`）拉取镜像，**不新增「集群 → 管理端」方向网络策略**。
>
> 日期：2026-08-10 ｜ 状态：**已实现，并经生产真机验证**；最初为方案，同日完成实现与单测
>
> **2026-08-21 架构演进注记**（初版落地后又经四轮真机修复，下文部分机制描述为初版记录，冲突处以本注记为准）：
> 1. **流池化**：隧道由「每集群一条共享流 + frame id 多路复用」改为**每集群流池（默认 16 条，`OPSGUARD_TUNNEL_POOL` 可调、两端须一致）**，一请求独占一流；§4.2 的 `streams`/waiter/dispatch 机制已整体删除。
> 2. **请求方向分帧**：`TunnelFrame` 新增 `req_chunked=10`，push 大请求体按 2MiB 帧流式上传，server 侧经 `io.Pipe` 流式消费（不再整包入内存）。
> 3. **push 双向化**：worker `/v2/` 方法白名单从 GET/HEAD 放宽到 GET/HEAD/POST/PUT/PATCH（DELETE 等 405）；`RoundTripStream` 请求体参数 `[]byte`→`io.Reader`；新增上传 `Location` 头相对化改写。
> 4. **吞吐与超时**：两端 gRPC 流控窗口 32MiB/流 + 64MiB/连接、keepalive 15s/5s 判死回收；worker HTTP `ReadTimeout=WriteTimeout=0` + `IdleTimeout=120s` 兜底（大层 push 502 修复，worker 1.2.7）。
>
> 详见 `deploy/offline/README.md` 记录 15/16 与《OpsGaurd-系统技术总览.md》§5.3。
>
> 关联：《K8s替换方案.md》（镜像源从 Harbor 可选切换）、`deploy/offline/README.md`（189.6 管理端 + 灾害集群 5 节点拓扑）、Worker-设计方案 §P6（gRPC 管理面）。

## 一、背景与现状

### 1.1 网络拓扑与策略（现状实测）

```
10.60.189.6（管理端，单机）
├── opsguard-server  :8080   页面+API + 内嵌 OCI 仓库 /v2（gin，同端口挂载）
└── opsguard_worker  manager 角色

10.60.171.x 灾害集群（5 节点，worker 为 global 服务，mode:host）
├── 232 (b-1)  swarm Leader + worker manager 角色   :6060 HTTP / :6061 gRPC
├── 230/249/253/231  node 角色
```

- 防火墙已放行 **189.6 → 232:6060-6064**（server 主动连 worker 的方向）；**232 → 189.6:8080 刻意未开**，也**不想开**。
- 结论先行：本方案的隧道内数据流是「worker→server 的帧跑在 **server 发起的流**上」——与 IdP 反向隧道完全同向，**不需要任何新增防火墙规则**。

### 1.2 现成范式：IdP 反向隧道（可直接复用的骨架）

`proto/opsguard.proto` 的 `Tunnel` RPC 已是现成的 HTTP 反向隧道：

| 端 | 代码 | 职责 |
|---|---|---|
| Server | `OpsGaurdWeb/server/internal/idptunnel/manager.go` | 每注册集群一个流池（默认 16 条 bidi 流），断线指数退避重开 |
| Server | `workerproxy/tunnel.go` `ServeTunnel` | 收 worker 转发的 HTTP 请求帧 → 代理到本机 `localBase`（`http://127.0.0.1:8080`）→ 回响应帧（**已带响应头**） |
| Worker | `internal/idpproxy/handler.go` | 集群内服务经 `/idp-proxy/` 走隧道访问管理端 IdP（r-nacos OIDC 生产在用） |
| Worker | `internal/grpcapi/tunnel.go` `TunnelManager` | 流池 borrow/release，每请求独占一条 bidi 流 |

关键事实：**隧道本来就是「通用 HTTP 中继」**（现为流池化，一请求独占一流）。IdP 与镜像中继共用同一 `Tunnel` RPC，互不干扰——不需要新 RPC、不需要第二个端口。

### 1.3 管理端内嵌 registry（拉取目标）

`internal/registry/`（gin，`Any("/v2/*rest")`，文件存储 `data/registry/`）：

- 完整 OCI 分布协议：manifests（schema2/OCI/index 透明）、blobs（内容寻址）、tags、分片上传（页面传包构建用）；
- `/v2/` 探活已回 `Docker-Distribution-API-Version: registry/2.0`（`handlers.go:88-90`）——dockerd 需要的头已齐；
- 可选 basic auth（`registry.users` 未配则匿名放行，`handlers.go:79`）。

### 1.4 三个绕不开的事实（决定方案形态）

1. **swarm 拉镜像是每节点本地 dockerd 的行为**——dockerd 只认 HTTP registry，不认识 gRPC。中继必须在节点上落一个「本地 registry 端点」（HTTP），再由它走隧道。
2. **隧道仅在 manager-role worker 启用**（`Worker/cmd/worker/main.go` 的 `if isManager` 守卫，node 角色不监听 gRPC；每集群为流池，默认 16 条并发流）。→ 中继点**只能先落在 232 一个 worker 实例**上，其余节点经集群内网指向 232 的代理端口（集群内互通是 swarm 运行前提，天然可用）。
3. **现有 `TunnelFrame` 是单帧 request/response**：server 侧 `proxyOne` 用 `io.ReadAll` 全量读入单个 `bytes body`（`workerproxy/tunnel.go:91`），两端 gRPC 均为默认 4MiB 消息上限（全仓库未显式配置 `MaxRecv/SendMsgSize`）。Java 镜像 layer 动辄几百 MB——**这是本方案要解决的核心缺口**。

### 1.5 缺口清单（修正后的准确版）

| # | 缺口 | 位置 | 方案 |
|---|---|---|---|
| G1 | 大 body 单帧传输 + 4MiB 上限 | proto + tunnel.go 两端 + TunnelManager | 分片流式帧（§三） |
| G2 | server 侧 `http.Client{Timeout:15s}` | `workerproxy/tunnel.go:50` | blob 下载改为流式无死限（§五） |
| G3 | 中继点拓扑（隧道只在 232） | `Worker/cmd/worker/main.go` `if isManager` | 首发单点中继；P3 演进逐节点隧道（§八） |
| G4 | 无路径白名单：隧道可打到本机任意 HTTP（含 /api） | `ServeTunnel` 的 proxyOne | 限定 `/v2/` + IdP 路径（顺手收敛横向面，§五） |

> ~ 响应头**已通**：`TunnelFrame.headers` 为请求/响应共用字段，server `proxyOne` 已回填、worker `RoundTripHTTP` 已解包（`tunnel.go:162-168`）。`Docker-Content-Digest`/`Content-Length` 会原样回到 dockerd。

## 二、总体设计

### 2.1 拓扑与数据流

```
                            ┌──────────── 灾害集群（10.60.171.x）────────────┐
  节点 dockerd（每台）        │                                              │
   ├─ 230/249/253/231 ─────►│ 10.60.171.232:6060/v2/*   （集群内网，已通）    │
   └─ 232（本机）──────────►│ 127.0.0.1:6060/v2/*                            │
                            │      │                                         │
                            │  232 worker（manager 角色）                      │
                            │   └ 新增 /v2/ handler（registry 转发，纯搬运）    │
                            │      └ TunnelManager（流池，每请求独占一条双向流）│
                            └──────────┬──────────────────────────────────┘
                                       │ 现有隧道流（server 发起，无新策略）
                            ┌──────────▼──────────────────────────────────┐
                            │ opsguard-server（189.6）                      │
                            │  ServeTunnel → proxyOne（改造：流式 + /v2/ 白名单）│
                            │    └ http://127.0.0.1:8080/v2/*（内嵌 registry）│
                            └──────────────────────────────────────────────┘
```

一次拉取（以 blob 为例）：

```
dockerd GET /v2/<name>/blobs/sha256:… 
  → 232 worker /v2/ handler（GET/HEAD/POST/PUT/PATCH 白名单，若未缓存）
  → TunnelManager.RoundTripStream：发请求帧（id=X）
  → server 收到 X → 代理到本机 registry → 读响应体分片 → 回 N 个帧（id=X, chunk_seq=0..N-1, 末帧 eof）
  → 232 worker 流式收到分片 → 边收边写回 dockerd（含 Content-Length/Docker-Content-Digest 头）
  → dockerd 本地摘要校验（sha256 不符会自动失败重试——天然防截断兜底）
```

### 2.2 复用与不新建

| 复用 | 不新建 |
|---|---|
| 同一 `Tunnel` RPC 的流池（每集群默认 16 条，一请求独占） | 新 RPC / 新长连接 / 新端口 |
| `idptunnel.Manager` 每集群流的开/重连生命周期 | 新的流管理器 |
| registry 内嵌实现的全部 v2 语义（manifest/blob/tags/auth） | worker 侧 registry 协议实现——只做字节搬运与方法白名单（GET/HEAD/POST/PUT/PATCH） |
| 内嵌 registry 的 basic auth（server 侧代持账号） | 节点侧凭据 |

### 2.3 两阶段路线

- **阶段一（本次实施）**：中继点 = 232 单点。所有节点 daemon.json 统一指向 `10.60.171.232:6060`（含 232 本机）。改动最小、隧道拓扑与现状一致。
- **阶段二（P2/P3，可选演进）**：中继侧磁盘 blob 缓存（§七）；放开 node 角色隧道的逐节点中继（§八），回到 `127.0.0.1` 每节点本地端点。

## 三、协议扩展（proto）

`proto/opsguard.proto` 的 `TunnelFrame` 追加两个分片字段（复用于 request 帧，不破坏旧语义）：

```proto
message TunnelFrame {
  string id = 1;
  string method = 2;
  string path = 3;
  repeated TunnelHeader headers = 4;
  bytes body = 5;
  int32 status = 6;
  string error = 7;
  // 分片流式（镜像中继用）：chunk_seq 从 0 递增；chunk_eof=true 标记末帧。
  // 响应体 ≤ 2MiB 时单帧（chunk_eof=true），更大 body 拆多帧；
  // 请求方向同样分帧（req_chunked=true，push 大层流式上传）。
  int32 chunk_seq = 8;
  bool chunk_eof = 9;
  bool req_chunked = 10;
}
```

**兼容规则**（proto3 未知字段忽略，新旧混排安全）：

| 场景 | 行为 |
|---|---|
| 新 server → 新 worker | 正常分片流式 |
| 旧 server → 新 worker | 旧 server 永不发分片（无大 body 能力），单帧且**不带 eof 标志**；worker 读侧按响应头 `Content-Length` 兜底判定结束 ✓ |
| 新 server → 旧 worker | 旧 `TunnelManager.takePending` 只取**首帧**即回 → dockerd 拿截断 body → **摘要校验失败显式报错**，不会静默脏数据；升级期可接受（建议先升 worker 再升 server 规避） |
| 请求帧（worker→server） | 大请求体（push 层）以 `req_chunked=true` 分帧流式上传；小请求仍单帧 |

**gRPC 消息大小**：两端显式放宽留余量——worker gRPC server 选项（`MaxRecvMsgSize/MaxSendMsgSize = 16MiB`）与 server 侧 `grpc.NewClient` 的 `MaxCallRecvMsgSize/MaxCallSendMsgSize = 16MiB`；**分片尺寸取 2MiB**（远低于默认 4MiB 上限兜底），并发多路时单连接内存 ≈ 2MiB × 在途帧数，可控。

## 四、Worker 侧改动（`Worker/internal`）

### 4.1 新增 `internal/registryproxy/`（对标 `internal/idpproxy/`）

- **挂载**：`Worker/cmd/worker/main.go` 在 `isManager && tunnel 可用` 条件下 `mux.Handle("/v2/", …)`（与 `/idp-proxy/` 同闸门）；路径加入 `authzMW.PublicPaths`（dockerd 无 bearer 能力，与 `/idp-proxy/` 同待遇）。
- **协议**：**纯静态转发，不解析 registry 协议**。方法白名单 `GET/HEAD/POST/PUT/PATCH`（push 双向化后放行上传，见头部演进注记 3）；`DELETE` 等其余方法回 `405`。
- **无发现改写**：不做 IdP 那套 discovery JSON 重写（`idpproxy/handler.go:91-96` 是 OIDC 特例），头/体原样透传。

```go
// 抽象隧道，便于单测（同 idpproxy.TunnelSender 思路；实现 = grpcapi.TunnelManager）
type TunnelStreamer interface {
  Available() bool
  RoundTripStream(ctx context.Context, method, path string, headers http.Header, body io.Reader) (status int, respHeader http.Header, stream io.ReadCloser, err error)
}
```

- Handler 逻辑：`Available()` 门禁 → 仅放行 `GET/HEAD`（其余 405）→ 透传完整 path/query/headers（含 `/v2` 前缀，server 侧 registry 需要）→ `RoundTripStream` → 回写状态码 + 透传头（跳过 hop-by-hop，含 `idpproxy.isHopByHop` 同款实现）→ **边收边写**（`w.(http.Flusher)` 每帧 flush），不在 worker 内存整包缓冲。

### 4.2 `TunnelManager` 的流式路径（`RoundTripStream`）

> 【2026-08-21 更新】初版的 `streams` waiter/dispatch/detach 多路复用机制已整体删除，现行实现为**流池模型**：

- 每集群默认 16 条 `Tunnel` bidi 流（`OPSGUARD_TUNNEL_POOL` 可调）；`borrow` 取一条空闲流（跳过死流），请求独占，`release` 归还；`offer` 不设上限（server 重开新流时不丢弃）。
- 每条流独立 recv loop；请求体大时以 2MiB 帧分片上行（`req_chunked`），响应侧同样按帧流式读出（`chunk_eof` 结束，`Content-Length` 兜底兼容旧端）。
- 超时：大 blob 无固定死限；结束判定靠 `chunk_eof`/`Content-Length` + dockerd 侧 digest 校验兜底；死流由 gRPC keepalive 判死后 teardown 重开。

## 五、Server 侧改动（`OpsGaurdWeb/server/internal/workerproxy`）

### 5.1 `ServeTunnel` 的 `proxyOne` 改为可流式（`proxyOneStream`）

```go
// 一流一请求：每条池流独立 recv loop，server 侧 io.Pipe 流式消费分帧请求体；增加：
// 1) 路径白名单（allowedPath）：仅放行 IdP 端点 + /v2/* + 可配置 extra 前缀；
//    非白名单返回 403 error 帧（见 G4/R4）
// 2) 响应体 ≤ 2MiB → 单帧（带 status+headers+chunk_eof）
//    更大 body → 读 2MiB 一块逐帧 Send（同 id、chunk_seq 递增）；
//    数据与 EOF 分帧到达时补一条空终止帧（chunk_eof=true），
//    worker 无需依赖 Content-Length 判断结束
// 3) IdP 用 http.Client{Timeout:15s}；registry 用无死限 client，
//    大 blob 生命周期由流 context 绑定（避免 15s 掐断）
// 4) registry 请求：relay 凭据注入（RelayConfig.RegistryUser/Pass）
//    SetBasicAuth 后转发；集群侧 dockerd 匿名访问本地端点
// 5) push 上传 3xx 的 Location 头相对化改写（回址指向本地中继端点）
```

### 5.2 registry 鉴权注入

- `registry.users` 为空（匿名 registry）→ 直连，零改动；
- `registry.users` 非空 → server 侧用 `registry.relay` 配置账号（缺省回退到 users 首个条目）注入 basic auth 后再代理；节点侧 dockerd 始终匿名访问本地端点。
- 配置：server.yaml `registry` 块新增 `relay: { enabled: true, username: …, password: … }`（缺省 enabled=true）。
- 「内嵌 registry 直连本机 loopback」与「构建 push 走本机」互不影响。

### 5.3 配置开关

- server.yaml `registry` 块新增 `relay`（缺省 enabled=true）；`registry.users` 非空且未配 `relay` 账号时自动回退首个 users 条目（默认配置开箱可用）；
- worker env：`OPSGUARD_TUNNEL_BASE` 门禁（配置即启用 IdP 隧道与 `/v2` 中继）+ `OPSGUARD_TUNNEL_POOL`（流池大小，须与 server 侧一致，缺省 16）。

## 七、缓存增强（已实现，2026-08-10）

- 位置：**worker 侧 `/v2/` handler 之内**（隧道入口），内容寻址磁盘缓存 `<dataDir>/registry-cache/blobs/sha256/<hex>/data`（与 server 内嵌 registry 同布局）：
  - blob GET（路径命中 `sha256:` 64 hex digest）：命中 → **直接从磁盘流回 dockerd，不再过隧道**；未命中 → 走隧道，`200` 响应边流回边落盘，完整收到才原子发布（temp 文件 + rename），截断/非 200 一律不入缓存；
  - manifest / tags / ping 恒透传（小，无缓存价值）；
  - 内容寻址天然不变，无需失效逻辑；**LRU 裁剪**按 mtime 淘汰最旧 blob，总量超上限时清到上限一半（上限 = `OPSGUARD_REGISTRY_CACHE_MB`，MiB；缺省 0 = 不限）。
- 配置（worker env，无需重启 server）：
  - `OPSGUARD_REGISTRY_CACHE_DIR` 缓存根目录（缺省 `<dataDir>/registry-cache`）
  - `OPSGUARD_REGISTRY_CACHE_MB` 容量上限（MiB，缺省 0 = 不裁剪）
- 收益：多节点同镜像首拉只有**第一份**过隧道（232 出口带宽从 ×N 降为 ×1），隧道抖动对已缓存 blob 归零。
- 实现文件：`Worker/internal/registryproxy/cache.go`（`BlobCache`：`Get`/`PutWriter`/`Publish`/LRU）+ `handler.go`（命中短路 + Tee 落盘）+ `cmd/worker/main.go`（env 接线）+ 单测（`cache_test.go`、`handler_test.go` 命中/未命中/非 200 不缓存）。

## 八、演进：逐节点隧道（P3，可选，未做）

- 改造点：node 角色 worker 也监听 gRPC + 启用 `Tunnel`（放开 `main.go` 的 `if isManager` 守卫，按 agent config 开关）；`idptunnel.Manager` 从「每集群一条」扩为「每节点一条」；

## 九、风险与对策

| # | 风险 | 说明 | 对策 |
|---|---|---|---|
| R1 | 管理端带宽发夹 | 5 节点并发首拉同镜像 = server 同时出 5 份整流（单层几百 MB） | 首拉错峰（先拉镜像再发部署）；P2 磁盘缓存把隧道流量压到 ×1；doc 预留带宽估算 |
| R2 | 232 单点故障 | 中继点掉线期间节点拉取失败 | dockerd 重试 + 已拉镜像本地留存（`imagePullPolicy: missing` 后拉取不依赖中继）；swarm 本身对 232 有容灾，worker global 服务会重建 |
| R3 | 隧道断流截断 | 在途分片流被断（idptunnel 重连前） | dockerd 摘要校验失败自动重试，**不会静默脏数据**；worker 侧会话级空闲兜底退出 |
| R4 | 隧道被当任意 HTTP 代理 | 现状 `ServeTunnel` 可打到本机任意 HTTP（含 /api） | **本次一并收敛**：白名单 = IdP 路径 + `/v2/*`；worker 侧 GET/HEAD 白名单再挡一层 |
| R5 | 拉取面外扩 | 集群内任意持有节点凭证者可用代理 | 仅 GET/HEAD + 仅 `/v2/` 前缀 + 中继端点绑 232 发布端口；push 面仍走管理端页面/直连 |
| R6 | 混合版本截断 | 新 server + 旧 worker 期间分片只取首帧 | digest 校验兜底显式报错；升级顺序：先 worker 后 server 可完全规避 |
| R7 | docker 20.10（231/253）兼容 | 老 daemon insecure-registry + 摘要校验行为 | 与 27.3 一致的单次 agent 验证；231/253 如随 K8s 下线可不配 |
| R8 | registry.users 非空 | 节点侧匿名拉取被拒 | server 侧代持账号注入（§5.2）；建议新增专用只读账号而非复用管理账号 |
| R9 | leader 迁移 / 角色漂移 | 中继依赖 232 的 manager 角色 worker | 首发接受（232 为固定 Leader）；若需强保障直接进 P3 |
